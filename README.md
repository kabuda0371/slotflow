# slotflow

从一套电子发票业务链（Slot / Action / Process）里提炼出的**可插拔业务管线**设计。

## 一句话

把一条业务流程切成若干**卡槽（Slot）**，每个卡槽是一个具名的可扩展点；卡槽上挂**动作（Action）**；一条**业务链（Process）**按卡槽顺序推进，在每处取“已装配、已排序”的动作依次执行。

业务链只关心“有哪些步骤”，不关心“每个步骤具体由谁、以什么顺序完成”。

## 三个概念

| 概念 | 是什么 | 声明了什么 | 不声明什么 |
|------|--------|-----------|-----------|
| Slot 卡槽 | 具名的可扩展点 / 接缝 | 能力接口（能做什么） | 由谁来做 |
| Action 动作 | 卡槽能力的一个实现 | 我是谁（编码 + 类型） | 挂在哪、排第几 |
| Process 业务链 | 按卡槽顺序组织的流程 | 有哪些步骤、什么顺序 | 每个步骤的具体实现 |

## 为什么这么设计

**1. 开闭原则** —— 新增一个国家 / 租户 / 行业的行为，等于“加一个动作类 + 加一行装配配置”，业务链代码一行不改。差异不写进代码分支，而是写进配置。

**2. 声明式装配** —— 动作与位置彻底解耦。动作只回答“是什么”，运行态配置回答“挂哪个卡槽、按什么顺序”。同一张票在不同国家，可以装配出完全不同的动作集合。

**3. 一卡槽多动作、有序执行** —— 一个卡槽可挂 N 个动作，按 `sequence` 排序依次执行，天然支持“标品默认 + 行业扩展 + 客开覆盖”的逐层叠加。

**4. 上下文贯穿** —— 一个数据袋从链头流到链尾，各动作通过它读写中间结果，动作之间无需互相引用。

**5. 设计态 / 运行态分离** —— 设计态用注解与枚举登记“有哪些卡槽、哪些动作”；运行态用配置决定“这一次、这个租户、这个国家，到底走哪些动作”。两态各自演进、互不干扰。

**6. 链体无感知** —— 业务链代码里不出现任何国家 / 租户 / 行业分支，所有差异都外置到装配配置，链路本身保持稳定、可读、可测试。

## 心智模型

```
Process(业务链):   [卡槽 A] ──▶ [卡槽 B] ──▶ [卡槽 C]
                      │            │            │
Slot(卡槽):       "校验"        "补全"        "保存"
                      │            │            │
Action(动作,有序): a1 → a2     b1 → b2 → b3    c1
                (标品 → 国家) (默认 → 行业 → 客开)
```

## 边界与取舍

- 这是“设计思想的最小可执行内核”，刻意去掉了持久化、缓存、多租户隔离、AOP 等工程细节；它们可以在其上按需补回。
- 卡槽是有类型的编译期契约（接口），动作通过接口调用，保留类型安全；而“装哪些动作、按什么顺序”在运行期决定。
